## 2. Чи варто винести частину даних у NoSQL?

У базі з Lab1 є дві різні за характером групи даних:

1. **Довідники і поточний стан** - товари, ціни, залишки на складі, працівники, постачання.
   Тут потрібні транзакції, цілісність (зовнішні ключі, тригери на залишки) і складні вибірки.
   **Це залишається в PostgreSQL.**

2. **Історія продажів (чеки)** - замовлення і їх позиції. Особливості:
   - замовлення **майже завжди читається цілком**: відкрити чек, показати історію покупок клієнту;
   - після створення **не змінюється** - це історичний документ;
   - **дані в ньому мають бути знімком на момент покупки**: якщо товар потім перейменують або змінять ціну,
     у старому чеку має залишитись те, що було надруковано.
   - **це найбільша і найшвидше зростаюча частина бази**

   Щоб прочитати одне замовлення в SQL, треба з'єднати **8 таблиць**:
   `Order`, `OrderItem`, `Product`, `Category`, `Customer`, `Employee`, `Department`, `Store`.

**Висновок:** історію замовлень доцільно зберігати в **документній базі (MongoDB)** - одне замовлення = один документ
з усіма даними чека. Інші дані залишаються в PostgreSQL.

**Які при цьому аргументи проти:**
- дублювання даних: назва товару і дані клієнта повторюються в кожному документі, тому сирий обсяг більший;
- аналітика "по всіх замовленнях" (виручка по категоріях, звіти) у SQL пишеться і працює простіше;
- немає зовнішніх ключів: Mongo не перевірить, що товар з `productId` існує.

## 3-4. Реалізація

### Приклад документу замовлення в MongoDB (колекція `orders`)

```json
{
  "_id": 1042,
  "date": "2025-01-03T15:45:17Z",
  "total": 51059.10,
  "customer":   { "id": 2861, "name": "Олена Лисенко", "phone": "+380670002861" },
  "employee":   { "id": 222, "name": "Олег Ткаченко" },
  "department": { "id": 5, "name": "Дім і сад", "store": "Мегамаркет Центр" },
  "items": [
    { "productId": 4417, "name": "Засоби для посуду Max 4417", "sku": "SKU-004417",
      "category": "Засоби для посуду", "mainCategory": "Побутова хімія", "qty": 2, "price": 289.19 }
  ]
}
```

### Відповідність SQL-таблицям

| Поле документа | Таблиці PostgreSQL |
|---|---|
| `_id`, `date`, `total` | `Order` |
| `customer` | `Customer` |
| `employee` | `Employee` |
| `department` | `Department` + `Store` |
| `items[]` | `OrderItem` + `Product` + `Category` (+ батьківська `Category`) |

Гроші зберігаються як `Decimal128` (точний десятковий тип, аналог `numeric(18,2)` у PostgreSQL), а не `double`.

Індекси в Mongo створені як аналоги індексів з Lab1:
`customer.id` (аналог `idx_order_customerid`) і `date` (аналог `idx_order_date_brin`).

### Дані

Генеруються скриптом [sql/01_seed.sql](sql/01_seed.sql), потім переносяться в Mongo програмою ([Lab2/Migration.cs](Lab2/Migration.cs)).
Тобто **в обох базах ті самі дані**.

| | Кількість |
|---|---:|
| Магазини / відділи / працівники | 3 / 18 / 300 |
| Категорії / товари | 36 / 5 000 |
| Клієнти | 100 000 |
| Замовлення | 300 000 (за ~22 місяці) |
| Позиції замовлень | 1 199 450 |

Особливості генерації, щоб дані були схожі на реальні:
- дати замовлень зростають разом з `Id`;
- ~20% замовлень без клієнта (покупець без картки лояльності);
- популярність товарів нерівномірна: одні товари купують набагато частіше за інші;
- ціни залежать від категорії (продукти дешеві, електроніка дорога).

Тригери з першої лабораторної на списання/перевірку залишків при вставці в `OrderItem` у базі `bd_lab2` вимкнені:
порівнюється зберігання замовлень, а логіки складу в Mongo немає - інакше PostgreSQL робив би більше роботи.

## 5. Тестування швидкодії

### Методика

- Запити виконує одна програма ([Lab2/Benchmarks.cs](Lab2/Benchmarks.cs)).
- Міряється **повний час "запит -> результат прочитаний програмою"**. `EXPLAIN ANALYZE` у PostgreSQL і `explain()` у Mongo
  міряють тільки час усередині бази і рахують його по-різному, тому для порівняння не підходять
  (але вони є в [sql/02_queries.sql](sql/02_queries.sql) і [mongo/queries.js](mongo/queries.js) для демонстрації планів виконання запитів:
  чи використовується індекс, скільки рядків/документів переглянуто, як з'єднуються таблиці).
- Перед вимірюванням - **прогрів**, щоб не міряти "перший запуск".
- Параметри (Id замовлень, клієнтів, місяці) **випадкові, але з фіксованим seed**: обидві бази отримують ті самі значення
  в тому ж порядку, а повторний запуск дає ті самі запити.
- Багато повторів (до 2000) і статистика: **медіана і p95** (95% запитів швидші за це значення).
  Середнє теж наведене, але воно чутливе до поодиноких затримок (збірка сміття, диск).

### Тести

| Тест | Що імітує | PostgreSQL | MongoDB | N |
|---|---|---|---|---:|
| T1 | відкрити чек за номером | JOIN 8 таблиць за `Order.Id` | `find({_id})` | 2000 |
| T2 | історія покупок клієнта (10 останніх) | вибірка за індексом + JOIN 7 таблиць | `find({customer.id}).sort(date).limit(10)` | 1000 |
| T3 | каса пробиває новий чек (1-7 товарів) | транзакція: `INSERT Order` + `INSERT OrderItem` | `insertOne` | 1000 |
| T4 | звіт: виручка по категоріях за місяць | JOIN 4 таблиць + `GROUP BY` | `$match` -> `$unwind` -> `$group` | 30 |
| T5 | T2, але **без індексу** по клієнту | Seq Scan | COLLSCAN | 30 |

T3 для Mongo виконаний двічі:
- `w:1` - налаштування за замовчуванням: Mongo підтверджує запис, коли дані в пам'яті, а на диск журнал скидається пізніше (до 100 мс);
- `w:1, j:true` - чекати запису в журнал на диску. **Це аналог `COMMIT` у PostgreSQL**
  (`synchronous_commit = on` чекає запису на диск).

### Висновки

1. **Читання цілого замовлення (T1, T2) у Mongo в 2-4 рази швидше.** Документ лежить в одному місці і читається
   одним зверненням до індексу; PostgreSQL для того самого робить 7 з'єднань і десяток пошуків по індексах.
   Саме це і є головний аргумент для пункту 2.
2. **Вставка (T3) швидша в Mongo лише через різні гарантії збереження.** З `j:true` (така сама надійність, як у PostgreSQL)
   час майже однаковий - обидві бази впираються в запис журналу на диск.
   Вставка одного документа замість двох таблиць великого виграшу не дає.
3. **На аналітиці (T4) переваги Mongo немає** - бази приблизно рівні, PostgreSQL трохи швидша в усіх трьох запусках.
   Mongo мусить розгорнути (`$unwind`) масиви позицій з кожного документа, а документи важчі за рядки таблиць.
   Тобто денормалізація, яка прискорює T1-T2, для звітів нічого не дає.
4. **Без індексу (T5) Mongo в 2.5-6 разів повільніша.** PostgreSQL сканує вузьку таблицю `Order` (52 МБ),
   а Mongo - усі документи разом із вкладеними позиціями (~300 МБ даних, які ще й треба розпакувати).
   Висновок: у документній базі правильні індекси ще важливіші.
5. **Дублювання коштує місця**: без стиснення документи займають ~1.75x більше, ніж нормалізовані таблиці.
   Стиснення це компенсує на диску, але не в пам'яті.

**Загальний висновок:** MongoDB вигідна для сценарію "записати/прочитати замовлення цілком" (каса, особистий кабінет),
PostgreSQL - для звітів і запитів, які заздалегідь не передбачені. Оптимально - гібрид: довідники і склад у PostgreSQL,
історія чеків у MongoDB.

## 6. Графова база - Neo4j

### Навіщо граф у магазині

Задачі "разом з цим товаром купують" і "клієнтам, схожим на вас, сподобалось" - це обхід зв'язків
клієнт -> замовлення -> товар -> інші замовлення -> інші товари. У SQL це кілька self-join таблиці `OrderItem`,
а в графі - один шаблон шляху.

### Модель

```
(:Customer)-[:PLACED]->(:Order)-[:CONTAINS {qty, price}]->(:Product)-[:IN_CATEGORY]->(:Category)-[:SUBCATEGORY_OF]->(:Category)
```

Завантажено з PostgreSQL (ті самі дані): 100 000 клієнтів, 239 709 замовлень (з клієнтом), 957 777 зв'язків `CONTAINS`,
5 000 товарів, 36 категорій.

### Запити ([neo4j/02_queries.cypher](neo4j/02_queries.cypher))

1. CRUD: `CREATE`, `MATCH`, `SET`, `DETACH DELETE` - клієнт і його замовлення
2. Покупки клієнта - візуалізація підграфа
3. Топ-10 товарів за продажами
4. "Разом з цим товаром купують"
5. Персональні рекомендації для клієнта
6. Виручка по основних категоріях (через ієрархію `SUBCATEGORY_OF`)
7. Найкоротший шлях між двома клієнтами
